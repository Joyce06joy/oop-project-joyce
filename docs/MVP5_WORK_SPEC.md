## 0. 本轮目标与完成定义

将 MVP 1–4 已有功能整合为**单主窗口、三服务导航、可用于答辩的稳定 Qt Widgets macOS 客户端**，重点提升 UI 信息架构、视觉一致性、错误反馈、异步状态、Mac 显示体验、三客户端同时运行及 `.app` 打包能力。

**完成定义（DoD）**：

1. 单客户端使用统一主窗口，左侧切换 QQ / 微信 / 微博；QQ/微信有聊天与群组；微博主要好友与推荐；未开通服务显示开通引导。
2. 用户可在 Qt 界面完成已有业务的完整操作闭环，不必退回终端菜单或手动修改数据库。
3. 所有网络请求可视化呈现进行中、成功、失败、断线、结果未知；Qt GUI 线程不阻塞。
4. 允许在**同一台 Mac** 启动本地服务端与至少三个相互独立的 Qt 客户端进程，登录 Alice/Bob/Carol 演示。
5. 至少一种可复现的 macOS `.app` 打包流程及部署检查清单；独立启动与否需如实测试记录。
6. 新增 UI 测试和 MVP 1–4 回归测试执行结果；不以界面截图代替业务/通信正确性证明。

**非目标**：重新实现账号、好友、群规则、多态、消息路由；引入 QML 重写；云部署、移动端、音视频、文件传输、支付、推送服务、复杂动画；未经批准迁移数据库或修改协议语义。

## 2. 页面信息架构与窗口范围

### 2.1 窗口清单

| 界面 | 功能 | 关键状态/限制 |
|---|---|---|
| 启动/连接 | 显示本地服务端连接结果，手动重试 | 离线不假装登录成功 |
| 登录 | 统一账号密码、登录/注册跳转 | 密码遮蔽，保留非敏感正确字段 |
| 注册 | 昵称、生日、所在地、密码/确认、开通 QQ/微信/微博 | 注册仅在服务端事务成功后显示 ID |
| 主窗口 | 单实例内左侧服务导航；顶部当前用户、连接状态；内容区 | 服务切换不重建 TCP 连接 |
| 账号/设置 | 资料、服务开通、QQ–微信绑定/解绑、当前服务状态 | 由服务端授权、保存反馈 |
| 好友 | 搜索、申请、接收、拒绝、删除、备注、详情 | 当前服务隔离；在线事件更新 |
| 推荐 | 同平台共同好友、跨服务推荐、推荐理由 | 只推荐，不自动加好友 |
| 群组 | 群列表、申请/邀请、成员、权限、子群、群详情 | QQ/微信规则差异明确 |
| 策略切换对话框 | 展示切换影响，群主确认 QQ/微信规则 | 不删除成员、管理员和子群数据 |
| 聊天 | 单聊/群聊/子群聊、历史分页、消息状态、草稿 | 微博无聊天入口；权限按服务端结果 |

UI 类名若新增：例如 `MainWindowDXX`、`FriendPageDXX`、`GroupPageDXX`、`ChatPageDXX`、`AccountPageDXX`、`GroupPolicyDialogDXX`；**以仓库现存架构为准，避免重复建类**。所有新增**自定义 C++ 类**均以 `DXX` 结尾，独立 `.h/.cpp` 文件，Qt 自动生成类和非类文件不强制改名。

### 2.2 主窗口布局

- `QMainWindow` + 左侧服务导航（QQ / 微信 / 微博）+ 内部业务导航 + 主内容区；以 `QStackedWidget` 或等效可维护方案实现。
- 聊天区采用可调整的会话列表/消息内容分栏（可用 `QSplitter`）；管理页采用列表/详情布局。
- 默认窗口大小建议约 1100×720，可调整大小；合理最小尺寸，缩小时不遮挡主要确认/取消控件。
- 顶部始终显示：当前登录用户、当前服务、服务器连接状态；必要时展示未读总数。
- 当前服务与服务开通/登录状态分离。切换服务应恢复对应会话和页面状态，不混入其他平台好友/群/聊天数据。
- QQ 与微博共享展示 ID、微信独立 ID，所有详情页面明确标注服务；内部 ID 不直接当用户可见编号。

### 2.3 页面统一规则

- 公共设计 token：字体尺度、间距、强调色、危险色、圆角、图标尺寸、空状态；集中在一份 QSS/Theme 管理资源中。
- macOS 原生控件行为优先；不强求像素级复刻 QQ/微信。界面以“IM 聊天 + 信息管理工作台”混合风格呈现。
- 列表要有空状态、加载状态、错误状态；搜索返回空结果时有明确解释。
- 破坏性操作（删除好友、踢人、解散群、切换管理规则）有确认对话框，提示对象与影响。
- 输入校验应定位到具体字段，保留其他已正确填写的内容；禁止使用清空整张表单作为通用错误处理。
- 操作中避免重复提交；操作完成根据服务端真实返回更新 UI，不能只凭本地按钮点击立即伪造成功。
- 所有含用户资料和消息的日志必须脱敏，密码和会话令牌不得输出到普通日志。

## 3. 重点用户流程（完整闭环）

### 3.1 登录及服务切换

`启动客户端 → 显示连接状态 → 登录 → 列出已开通服务 → 用户确认联动登录 → 进入主窗口 → 左侧切换 QQ/微信/微博`。

- 未开通服务：显示开通引导；已开通未激活：先确认服务会话；已激活：直接进入。
- 退出登录后删除客户端持有的有效会话凭据、断开或重置相关连接态；新账号登录不得看到旧用户缓存。

### 3.2 好友申请实时反馈

`Alice 搜索 Bob → 发送申请 → 申请已提交 → Bob Qt 实时收到通知 → Bob 同意 → Alice/Bob 列表刷新`。

- 若 Bob 离线，重新登录后拉取待处理申请；推送只负责增量通知，列表以服务器数据为准。
- 对方拒绝/申请重复/网络超时，需要明确状态，不产生重复好友关系。

### 3.3 群组权限与多态

- QQ：支持申请、管理员、子群；微信：成员邀请、仅群主管理、不可创建子群。
- 在 QQ 所属群内切换为微信管理规则后，成员保持，QQ 管理员权限暂时停用，子群数据保留但不可用；切回 QQ 规则后恢复。
- 切换对话框需展示影响，且仅群主可以提交；最终权限由服务器校验。切换失败回到服务器确认的原状态，不可仅修改本地标签。

### 3.4 聊天与断线

`Alice 发送 → 本地“发送中” → 服务端事务确认“已保存” → Bob 收到 → 必要时送达/已读`。

- 离线时保留草稿；消息超时标识“状态待确认”，不得直接重发不同请求 ID 造成重复。
- 断线后状态横幅与重连提示，不冻结主窗口；重连成功后重新验证会话并同步数据，不假定旧 Session 永远有效。
- 历史按分页增量加载，切换会话不丢草稿；Qt 页面不能同步读取整个聊天历史。

## 4. Qt 事件、异步、线程与状态管理要求

1. UI 只在 GUI 线程更新；禁止从服务端/后台线程直接触碰 Widgets。
2. `QTcpSocket` 尽量遵循现有异步信号槽架构（`readyRead`、`connected`、`disconnected`、`errorOccurred`）；**不得在 GUI 主线程调用阻塞式 `waitFor...()`**。
3. 将消息/响应分发和 QWidget 显示逻辑解耦；通过已有 Controller/Facade/状态模型或 Qt signals 传递数据。
4. 网络事件存在乱序或重复可能：前台对请求用 `request_id` 关联响应，列表拉取用版本/最近更新时间或请求代际判断是否覆盖较新数据。
5. 视图刷新优先局部更新，不要每条消息都销毁并重建整个页面；避免连接同一信号多次导致重复处理。
6. 每种异步操作至少定义：`Idle → Loading → Success / Error / Unknown`；断线时另有 `Offline/Reconnecting` 全局状态。`Unknown` 表示超时后服务端是否提交不确定。
7. 页面生命周期安全：关闭/切换页面时不要让悬挂指针处理后续网络事件；遵循 QObject ownership 和安全连接断开规则。
8. 数据库操作仍在服务端，Qt 客户端不得直接打开/修改业务 SQLite 数据库。

## 5. Qt 页面验收的视觉与交互要求

- **登录/注册**：标准 Tab 焦点顺序、可见密码显示/隐藏选项（如已有则复用）、提交按钮禁用逻辑、错误字段定位、完成结果可复制。
- **好友管理**：服务标签清楚；好友详情含昵称、展示 ID、备注；能看到申请待处理状态和推荐理由。
- **群组**：成员角色可视化，群主/管理员/普通成员区分清楚；微信模式不显示无效管理员操作。
- **聊天**：发送者与接收者气泡区分、时间戳、加载更多、未读标识、发送状态；清楚显示群聊和子群聊。
- **连接状态**：服务器离线、登录失效、自动重连/手动重试可见，操作不会悄悄失败。
- **一致性**：UI 中操作权限和服务器校验结果一致，最终以服务器为准。
- **可用性**：键盘导航、Enter/Escape 在对话框中的合理行为、文本对比度、长昵称和超长消息换行/截断、空数据提示。
- **窗口布局**：在较小屏幕、常规 Mac Retina 和缩放窗口下内容不溢出、不覆盖主要按钮。

## 6. 多客户端本机演示规格

至少具备以下布局和路径：

- `IMServer`：监听 `127.0.0.1:8888`（若仓库已用不同端口，优先保持兼容并写明配置）。
- `IMClient`：同一可执行程序允许启动至少三个独立进程，各有独立登录会话：Alice/Bob/Carol。
- 可通过命令行参数、环境变量或用户级配置区分每个客户端窗口/日志位置，不能让实例 2 覆盖实例 1 的会话文件。
- 严禁使用“单实例锁”阻止多客户端演示（如已有须提供明确的可控演示方式）。
- Alice→Bob QQ 单聊，Alice→群成员群聊，Bob 离线重启后同步，群策略切换后权限变化，全部通过 Qt UI 展示。
- 数据库只由服务端写入；演示数据需可重置，重置操作不得在正常客户端启动时自动执行。

建议提供 `docs/DEMO_MVP5.md`，包含窗口摆放、启动顺序、演示账户来源（**不得把真实生产密码写进仓库**）、预置数据创建方式、失败后的重试步骤及截图证据清单。

## 7. macOS 工程构建与 `.app` 打包

1. 保持 Qt 6 + CMake，保证 Qt Creator 能打开并直接构建 Client 和 Server 两个目标。
2. GUI 客户端构建为 macOS application bundle（`.app`）；资源使用 Qt Resource System (`.qrc`) 或已有等效方案，不依赖开发机绝对路径。
3. 记录 Qt 安装来源、Qt 版本、编译架构（arm64/x86_64）、macOS 版本、CMake Preset/Kit（如适用）。
4. 检查 `.app` 包内 Qt 动态库与插件依赖；使用 `macdeployqt`（如环境提供）打包；记录实际命令及结果。
5. 验证从 Finder 启动 `.app`、启动服务端后的连通性、多个客户端实例、打包后资源加载、关闭与重启。
6. 检查应用图标、窗口标题、基础版本号；不要求 Apple 公证（notarization）或 App Store 发布，但若未签名/公证要明确 Finder/Gatekeeper 限制，**不得宣称可在任意 Mac 无警告安装**。
7. Server 可作为终端可执行程序交付，答辩时显示简明日志；不得假定服务器藏在客户端进程里。
8. 如执行环境不是 Mac 或缺少 Qt 工具，只提供可复现打包指令和静态构建检查，明确标记 macOS 实机验证“未执行”，不得伪造 `.app` 已验证。
